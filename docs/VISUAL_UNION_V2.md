# 纯视觉并集 v2 · 2026-10-20

负责人要求把当前 RallyClip 与剪辑痕迹结果取并集。新入口
`run_visual_union.ps1` / `tools/run_visual_union.py` 默认使用 fast v2，
`--mode full` 使用官方完整 CPU 路线。默认两线程，两个阶段顺序执行；
无需 GPU，也没有音频分析。原便携包、独立 full/fast 行为保持原样。

## 为什么不能直接合并旧结果

demo_cut 的原始 full/fast 最终数组都是空，但模型并非没看到活动：
full 的 869 个采样中 867 个 pointness ≥0.5，形成约172.64秒的长候选，
被上游 `max_duration_sec=60` 在合并前删除。实际骨架捕获中近端分配
802/869，远端1/869；缺远端是否导致持续高分尚未证实。负责人确认
此片近端确实持续打球，中间包含剪辑。

新路径重放保存分数，并核对原始解码结果一致，然后只恢复因超过时长上限
被删除的活动段。短段过滤、阈值、边界细化、模型权重均沿用上游。
恢复段与原有结果进入并集；最终长段继续保留待复核，不凭空每60秒切一次。
默认1秒内的剪辑边界吸附到动作边界，互不合并不同的动作边界。
完整边界来源和动作外分区也保留。剪辑本身不构成打球证据。

## demo_cut 结果

原视频720×404，当前作者模型拒绝低于720p。此次继续使用前次明确标识的
1284×720放大副本，放大不恢复细节；时间戳已与原片核对一致。
这不构成原生404p支持。放大转换先前耗时121.17秒，不能混入模型速度收益。

复用同一副本的 fast 分数，另跑4fps、宽320的既有 PySceneDetect 配置：

| 候选段 | 起止（秒） |
|---|---|
| 1 | 0.299–30.000 |
| 2 | 30.000–96.500 |
| 3 | 96.500–140.500 |
| 4 | 140.500–172.940 |

剪辑候选为30.0、96.5、140.5秒；各点前后约0.3秒的画面都显示明显人物
位置跳变。未按负责人提到的一次剪辑强行只留一个，也没有独立逐帧人工
切点真值，不能报告准确率。第二段66.5秒仍保留并标记超限待复核。

fast 原运行46.658秒，新增剪辑分析19.507秒，阶段计时相加66.165秒，
约为副本173.88秒时长的0.38倍。合并运行显式复用缓存，
该数字不是本次完整启动到结束的实测，也不含放大、导出或报告写入。
所有数据均来自本机CPU，不能代表业务服务器速度。

本地证据：`outputs/demo_cut_union_20261020/combined/fused/`、
`scene_probe/`、`cut_neighbors.jpg`；不上传私人视频或输出。
